# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## O que é

Sistema web interno de gestão de salas para secretarias de prédios da PUCRS. Nasceu no prédio 15 (Living 360) e é **multi-prédio por design** — cada prédio tem sua própria grade semanal, salas, equipe e dados isolados. A grade de horários vem do sistema acadêmico "Espaço Físico" da PUCRS (sem acesso direto ao banco): um PDF da agenda semanal é extraído, importado e publicado como JSON estático por prédio.

Idioma do domínio, comentários, commits e UI: **português**. Mantenha esse padrão.

Testes só cobrem funções puras ([tests/](tests/), `node --test`, sem test runner instalado): regras de horário do timeHelpers e de blocos/trocas de [aulasDoDia.js](src/utils/aulasDoDia.js), incluindo a **paridade** das chaves de bloco front × `computarChavesDeBlocos()`. Imports usados pelos testes precisam de extensão `.js`. "Verificar" = `npm run lint` + `npm test` + rodar `vercel dev` e exercitar o fluxo. O GitHub Actions ([ci.yml](.github/workflows/ci.yml)) roda lint + test + build em todo push na `main` e em pull request, sem segredo nenhum — mantenha os testes sem rede para continuar assim. Em [tests/api/](tests/api/) ficam testes de handler/service com um **Supabase falso** ([supabaseFalso.js](tests/api/supabaseFalso.js): troca `from`/`rpc`/`storage`/`auth` do client singleton por versões em memória — sem rede, sem banco): `withAuth`, travas da Gestão de Equipe, importação da grade, Painel Admin. Importe o `supabaseFalso.js` antes de qualquer módulo do backend (ele define as variáveis de ambiente do `createClient`) e os módulos do backend com `await import(...)`.

## Arquitetura — o que não é óbvio

**Grade é lida do CDN, não da API.** O caminho de leitura da grade **não passa por serverless**. O frontend ([useGrade.js](src/hooks/useGrade.js)) faz `fetch` direto do Supabase Storage público (`.../storage/v1/object/public/grades/grade_predio_{predioId}.json`) e cacheia em `window.__GRADE_CACHE`. A API (`/api/grade`) só serve `/api/grade/busca` (busca textual). Quando um PDF é importado, [grade.service.js](backend_core/services/grade.service.js) `gerarEPublicarIndexEstatico()` **regenera e sobrescreve** esse JSON no Storage. Consequência: alterar dados de grade no banco não reflete no front até republicar o JSON estático.

**Backend em 3 camadas, sempre nessa ordem:**
```
api/*/index.js  (handler HTTP: parseia URL, valida método/permissão, monta payload)
  → backend_core/services/*.service.js   (regra de negócio; cache em memória)
    → backend_core/repositories/*.repository.js  (queries Supabase)
      → backend_core/config/supabase.js   (client service-role)
```
Não coloque query no handler nem regra de negócio no repository.

**Roteamento da API é manual, não file-based.** [vercel.json](vercel.json) reescreve `/api/avisos/(.*)` → `/api/avisos/index.js` (idem emprestimos, equipe, grade, admin). Cada `index.js` **parseia `req.url` na mão** para extrair `id`/`ação` e despacha por `req.method` (ver [api/avisos/index.js](api/avisos/index.js) como referência do padrão: `GET /`, `POST /`, `GET /historico`, `PUT /:id/concluir`, `PATCH /:id/comentar`, `DELETE /:id`). Para adicionar uma rota, edite os `if (req.method === ... )` do handler — **não** crie um arquivo novo. O `api/avisos/[...rota].js` é só um `export { default } from './index.js'` (catch-all de segurança para subcaminhos).

**Autenticação e isolamento multi-prédio** ([withAuth.js](backend_core/middlewares/withAuth.js)): todo handler é exportado como `withAuth(handler, 'modulo')`. O middleware:
- valida o JWT (`supabase.auth.getUser`) com **cache em memória de 5 min** (`Map` + dedupe de requisições concorrentes; limpeza a cada 10 min);
- carrega `usuarios_acessos` (perfil, `predio_id`, `permissoes[]`);
- resolve o **prédio ativo**: usuário normal fica preso ao seu `predio_id`; só o usuário **global (= tem a permissão `admin`)** pode operar em qualquer prédio enviando o header **`x-predio-id`**. Prédio nulo sem admin = **órfão** (sem acesso), nunca global;
- injeta `req.user = { id, email, predio_id, permissoes, is_admin }`.

**Regra de ouro do multi-tenant:** dentro do handler use **sempre `req.user.predio_id`** — nunca releia `req.headers['x-predio-id']`. O `withAuth` já decidiu se o header vale (só p/ admin). Reler o header deixa um usuário comum forjar o prédio. Toda query no service filtra por esse `predio_id`. O 2º argumento (`'avisos'`, `'grade'`, ...) barra por módulo (admin sempre passa). Operações **por ID** (empréstimos) devem validar que o objeto pertence ao `req.user.predio_id` **e a um ponto que o usuário opera** (ver `_registroOperavel`/`_itemOperavel` em [emprestimos.service.js](backend_core/services/emprestimos.service.js)) — RLS não cobre a service role.

**Convenções de backend** (utils em `backend_core/utils/`):
- **Permissões:** [modulos.js](backend_core/utils/modulos.js) é a fonte única dos slugs (`MODULOS`) e de `sanitizarPermissoes(lista, {permitirAdmin})` (descarta valores inválidos; remove `admin` de quem não é admin). Gestor de equipe não-admin nunca concede `admin`.
- **Erros:** lance `new ErroPublico(msg)` para mensagens seguras ao usuário; qualquer outro erro vira 500 genérico + log via `responderErro(res, err)` ([http.js](backend_core/utils/http.js)). Não devolva `error.message` cru do banco.
- **Auditoria:** `registrarAuditoria({ user, acao, entidade, ... })` ([auditoria.js](backend_core/utils/auditoria.js), não-bloqueante) para ações sensíveis (permissões, convites, empréstimos). Requer a tabela `auditoria_log`. A leitura é a aba **Auditoria** do Painel Admin ([AuditoriaAdmin.jsx](src/components/AuditoriaAdmin.jsx)) via `GET /api/admin/auditoria` (só admin, últimos 500, todos os prédios). Ao criar uma `acao` nova, dê a ela um rótulo em `ACOES` (e, se tiver `detalhes` próprios, um caso em `resumir()`) nesse componente — senão a tela mostra o slug cru.

**Dois clients Supabase, papéis distintos:**
- [src/supabase.js](src/supabase.js) — **anon key**, respeita RLS. O front usa direto para: sessão/auth, ler `usuarios_acessos` ([useAuthAccess.js](src/hooks/useAuthAccess.js)), ler a grade no Storage, assinar Realtime e **gravar `trocas_sala`**.
- [backend_core/config/supabase.js](backend_core/config/supabase.js) — **service role**, ignora RLS, `persistSession:false`. Só no backend. Quase toda mutação passa pela API; a exceção é `trocas_sala`, escrita direto pelo front.

**RLS é parte da segurança, não opcional** ([supabase/migrations/rls_policies.sql](supabase/migrations/rls_policies.sql)): como o front acessa `usuarios_acessos`, `trocas_sala` e o Realtime direto com a anon key, o isolamento por prédio dessas tabelas vive no banco. É também onde a permissão `edicao_grade` é aplicada de fato (escrita em `trocas_sala`). A service role ignora RLS, então o backend não é afetado. Ao mexer nesses fluxos, ajuste a policy junto.

**Contatos é o único módulo global.** O diretório institucional (Escolas da PUCRS, unidades de atendimento, índice curso→Escola e serviços do Living 360) vive em `contatos`/`contato_cursos` **sem `predio_id`** — é o mesmo dado para todos os prédios. Consequências: o handler ([api/contatos/index.js](api/contatos/index.js)) ignora `req.user.predio_id`; a queryKey do [useContatos](src/hooks/useContatos.js) é só `['contatos']` (sem prédio); e a aba não passa por `hasPredioContext`. `GET` devolve a árvore inteira (~30 contatos + ~210 cursos) numa chamada, então **a busca é client-side** — [contatosBusca.js](src/utils/contatosBusca.js) é a fonte única dessa regra, usada tanto pela tela quanto pela barra de busca global do Dashboard.

**Contexto de prédio no front:** [PredioContext](src/contexts/PredioContext.jsx) guarda `predioAtivo` em `localStorage` e o `predioNome` legível (preenchido pelo [SeletorPredio](src/components/SeletorPredio.jsx); usado no cartaz de troca: o logo do Living 360 só sai para o prédio 15, os demais levam o logo da PUCRS + o nome do prédio). O [Dashboard](src/components/Dashboard.jsx) monta os headers de toda chamada autenticada com `Authorization: Bearer <token>` + `x-predio-id: <predioAtivo || acesso.predioId>`. Ao chamar a API, sempre propague esses dois headers.

**Rotas do front (React Router, `BrowserRouter` no [main.jsx](src/main.jsx)).** Cada tela do Dashboard tem URL própria; [rotas.js](src/rotas.js) é a fonte única dos caminhos e o [Dashboard](src/components/Dashboard.jsx) renderiza `<Routes>` (as abas são `NavLink`). Tela nova = caminho em `ROTAS` + `<Route>` + aba/item do menu Gestão. Tela com permissão passa por `restrita(canView*, elemento)`, que manda URL digitada sem permissão (ou sem prédio) de volta para `/` — use a **mesma** flag que esconde a aba. A Planta fica em `/` **sem redirect** de propósito: o link de convite chega como `/#access_token=...` e um `<Navigate>` na raiz apagaria o hash. A busca global gera links (`/linha-do-tempo?dia=&filtro=`, `/contatos?id=`). O fallback de SPA no [vercel.json](vercel.json) é `/((?!api/|@)[^.]*)` → `/index.html`. Ficam de fora caminhos com ponto (assets) e `/@...` (módulos virtuais do Vite): um catch-all `/(.*)` faz o `vercel dev` servir `index.html` no lugar do JS (tela branca). Consequência: caminho de rota **não pode ter `.`**.

**Layout de celular (até 768 px).** Mesmo app, mesmas rotas e mesmo visual (tokens de `index.css`); muda só a arrumação. [useCelular()](src/hooks/useCelular.js) (`matchMedia`, mesmo limite do CSS) decide a estrutura e [celular.css](src/celular.css) o resto. No celular o [Dashboard](src/components/Dashboard.jsx) troca Topbar + abas por [TopoCelular](src/components/celular/TopoCelular.jsx) (só o período atual; o `SeletorPredio` precisa estar montado nos dois layouts, é ele que fixa o prédio de quem não é admin) e [BarraInferior](src/components/celular/BarraInferior.jsx) (as mesmas abas + **Mais**, rota `/mais` → [MenuMais](src/components/celular/MenuMais.jsx) com Contatos, Empréstimos, Gestão, perfil, tema e Sair). A busca vira [BuscaCelular](src/components/celular/BuscaCelular.jsx) em tela cheia com os **mesmos** resultados do dropdown (`resultadosBusca`); ela fica sempre montada porque o foco no campo tem que acontecer dentro do toque (senão o iPhone não abre o teclado). Planta: "Consultar sala" (teclado numérico) + [PainelSala](src/components/celular/PainelSala.jsx) no toque — a regra é `situacaoDaSala()` de aulasDoDia, a mesma do resultado de sala da busca do topo. Linha do tempo: [MiniGrade](src/components/celular/MiniGrade.jsx) (cada aula é um bloco com as letras dos períodos e o nome; rola para os lados com a sala parada e abre no período atual; tocar na aula abre os detalhes, tocar na sala abre a agenda) e [AgendaSala](src/components/celular/AgendaSala.jsx) (`?sala=`); regras puras em [miniGrade.js](src/utils/miniGrade.js) sobre os `slots` que a Timeline já monta (a regra de blocos continua uma só). A Timeline também lê `?aula=<chave>[&trocar=1]` (vem do painel da sala). Modais de troca: classes `modal-folha`/`modal-tela-cheia`/`modal-cartao`/`modal-acoes` viram painel que sobe/tela cheia só no CSS de celular; `so-computador`/`so-celular` escondem por layout. **No celular não se imprime o cartaz** (decisão do usuário): os botões de imprimir são `so-computador`. Telas de gestão e o balcão de empréstimos abrem como no computador, com o aviso de `TELAS_DE_COMPUTADOR`. Tema: [useTema()](src/hooks/useTema.js) no Dashboard (vale nos dois layouts; atualiza a `meta theme-color`). Ícone na tela de início: [manifest.webmanifest](public/manifest.webmanifest) + `public/icones/` + tags no `index.html` (sem service worker; no iPhone o ícone tem login separado do Safari). Regra antiga a lembrar: `index.css` tem `#app { display: none }` — por isso o seletor é `#app.app-celular`. Campos ficam com 16 px no celular (abaixo disso o iPhone dá zoom).

**`timeHelpers.js` é código compartilhado front+back.** Mesmo estando em [backend_core/utils/timeHelpers.js](backend_core/utils/timeHelpers.js), os componentes React o importam via caminho relativo (`../../backend_core/utils/timeHelpers`). É a **fonte única** de: `PERIODS` (períodos PUCRS A–P com horários), `getCurrentPeriod()` (usa timezone `America/Sao_Paulo` e "ponte" um intervalo ≤30 min para o período seguinte), `groupConsecutiveClasses()` (agrupa períodos consecutivos da mesma sala/aula), `getDiaAtual()`, `extractPeriodCode()`, `isInternalClass()`. Nunca duplique período/horário em componente — importe daqui.

**Estado no front:** TanStack Query (`staleTime` 5 min, sem refetch no foco — [main.jsx](src/main.jsx)) + Supabase Realtime para push. Badge de avisos no Dashboard: `useQuery` na **mesma** key do MuralAvisos (`['avisos', predioId, userId]`) e com a **mesma** `queryFn` (`buscarAvisos` exportada de [useAvisos.js](src/hooks/useAvisos.js)); o canal Realtime do Dashboard invalida essa key em qualquer mudança. Nunca crie observer sem `queryFn` nessa key: ele sobrescreve as opções da query e quebra os refetch do Realtime ("No queryFn was passed"). **Trocas aparecem em todas as telas de grade:** Planta, Próximas aulas e a busca do topo (sala consultada) usam [aulasDoDia.js](src/utils/aulasDoDia.js) (`slotsDoDia`/`blocosDaSala`/`trocaNoPeriodo`), que espelha a regra de blocos da Timeline e de `computarChavesDeBlocos()`. Badge de trocas: [useTrocasSala](src/hooks/useTrocasSala.js) (fetch próprio + Realtime, key `['trocas_sala', predioId, <data de hoje>]`, compartilhado com a Timeline; devolve só as trocas vigentes — ver "Trocas de sala" abaixo), contando só trocas cuja chave existe na grade atual via `computarChavesDeBlocos()` do timeHelpers — que espelha a regra de blocos da Timeline; ao mudar uma, mude a outra.

**Cache em memória nos services.** `grade.service.js` mantém `gradeCacheMap` por prédio; `processarUploadCsv` o invalida (`= null`) após republicar. Serverless é efêmero, então trate esse cache como best-effort.

## Pipeline de importação de grade (PDF → CDN)

1. [UploadPDF.jsx](src/components/UploadPDF.jsx) envia `multipart/form-data` para `POST /api/grade/importar-pdf` — exige o módulo **`edicao_grade`** (o mesmo da tela; antes aceitava `grade`, o de leitura). O Histórico de aulas (BI) usa `POST /api/grade/analisar-pdf` (módulo `relatorios`), que repassa o PDF ao endpoint `/analyze-bi` do extrator — o navegador não chama mais o extrator direto (`VITE_PYTHON_API_URL` não é mais usada no front). Rotas com arquivo próprio em `api/grade/` precisam de rewrite explícito no [vercel.json](vercel.json) **antes** do catch-all `/api/grade/(.*)`.
2. Handler ([importar-pdf.js](api/grade/importar-pdf.js)) desliga o bodyParser (`export const config = { api: { bodyParser: false } }`) e usa `formidable` via `lerPdfDoFormulario()`.
3. `grade.service.processarUploadPdf()` repassa o buffer para a **API Python externa** (`PYTHON_API_URL`, hoje na Vercel — `python-extractor.vercel.app`), com timeout de 90 s e uma nova tentativa em erro de rede/5xx; falha vira `ErroPublico` 502 (ou 422 se o extrator recusar o PDF). O upload é lido por [uploadPdf.js](backend_core/utils/uploadPdf.js): limite de 4,4 MB ([limites.js](backend_core/utils/limites.js), o mesmo que as telas conferem antes de enviar — a Vercel recusa corpo > 4,5 MB), assinatura `%PDF-` conferida no conteúdo e temporário sempre apagado.
4. A resposta (`records`) é normalizada — `simplificarSala()` converte códigos `C.xx.xx.andar.sala` no número curto da sala.
5. PDF sem nenhuma aula reconhecível é **recusado antes de tocar em qualquer coisa** (422, a grade atual fica). Salas que o prédio ainda não conhecia são **criadas como `Pendente`** (as existentes não são tocadas), a grade é trocada pela RPC `grade_substituir` (DELETE+INSERT numa transação: ou entra a nova inteira, ou fica a antiga; sem a função no banco, `substituirGrade` cai no delete+insert antigo), a importação vai para a auditoria (`grade.importar`) e `gerarEPublicarIndexEstatico()` republica o JSON no Storage — se a publicação falhar, a resposta é erro 502 (antes dizia sucesso e as telas seguiam com a grade antiga). Leitura da grade (`buscarGradeCompleta`) é **paginada**: o PostgREST corta em 1000 linhas sem erro. A resposta traz `salasParaDecidir` (+ `primeiraImportacao`) e o [UploadPDF](src/components/UploadPDF.jsx) abre a pergunta "exibir / manter oculta" ([DecisaoSalasNovas.jsx](src/components/DecisaoSalasNovas.jsx)).

## Salas visíveis por prédio

O PDF traz tudo o que tem agendamento no prédio, inclusive espaços que não são sala de aula (auditório, evento, manutenção). `salas.status` decide o que aparece: `Ativa` (visível), `Oculta` (escolhida para não aparecer) e `Pendente` (sala nova vinda de uma importação, oculta até alguém decidir). Regras e textos em [backend_core/utils/salas.js](backend_core/utils/salas.js) (backend) e [src/utils/salas.js](src/utils/salas.js) (front), cobertas por `tests/salas.test.js`.
- **O filtro é na publicação, não nas telas:** `gerarEPublicarIndexEstatico()` só põe no JSON as salas visíveis e os agendamentos delas (`filtrarPublicacao`), e `_obterGradeOtimizada()` (busca do topo) faz o mesmo. Nenhuma tela do front sabe que salas ocultas existem — não filtre de novo em componente. Os agendamentos das ocultas continuam no banco: reexibir a sala os traz de volta sem reimportar.
- **Re-import preserva a escolha:** `inserirSalasNovas` usa `ignoreDuplicates` — nunca faça `upsert` de sala com payload parcial (o supabase-js preenche coluna ausente com `null` e apagaria o `status`).
- **Tela Gestão → Salas do Prédio** ([SalasPredio.jsx](src/components/SalasPredio.jsx)) via `GET/PUT /api/grade/salas` (`edicao_grade`, mesmo gate de importar o PDF). O `PUT` republica o JSON, registra `grade.salas.visibilidade` na auditoria e dispara `avisarGradeRepublicada()` ([useGrade.js](src/hooks/useGrade.js)), que faz todas as instâncias montadas de `useGrade` recarregarem.

## Modelo de permissões

`usuarios_acessos.permissoes[]` (array de strings = os `id` de `sistema_modulos`, que são slugs; fonte única em [modulos.js](backend_core/utils/modulos.js)). Módulos: `admin` (global, todos os prédios), `grade`, `avisos`, `emprestimos` (operar o balcão dos pontos vinculados), `gestao_emprestimos` (acervo, limite, suspensões; vê todos os pontos do prédio), `relatorios`, `edicao_grade`, `equipe`, `edicao_contatos`, `relatorio_emprestimos_rede` (ver "Relatório da rede" abaixo). `admin` sempre passa e é o **único** caminho para acesso global (prédio nulo sem admin = órfão — a exceção é o login do relatório da rede, que só vê esse relatório). O Dashboard deriva as flags `canView*` combinando permissão + `hasPredioContext`; espelhe a **mesma** checagem no backend via `withAuth(handler, 'modulo')` — nunca confie só no gating de UI. Exceção importante: `edicao_grade` (criar troca de sala) é escrito direto pelo front em `trocas_sala`, então sua verificação vive na **RLS**, não num handler. O handler de empréstimos também é `withAuth(handler, null)` e checa por grupo de rota (`podeOperar`/`podeGerir`/`podeVerRelatorio` do service), porque o relatório aceita `relatorios` e a gestão tem módulo próprio. Outra exceção: **Contatos** não tem módulo de visualização — a aba é visível para todo usuário autenticado (o handler é `withAuth(handler, null)`) e só a escrita é gated, por `edicao_contatos`, checado dentro do handler. "Autenticado" aqui é membro da equipe: conta órfã (sem prédio e sem admin) leva 403 — o cadastro público do Auth está ligado no Supabase, então ter sessão não prova ser da equipe.

## Banco / Supabase

Tabelas principais: `predios`, `salas`, `usuarios_acessos`, `perfis`, `sistema_modulos`, `avisos`, `trocas_sala`, `emprestimo_pontos`, `emprestimo_ponto_usuarios`, `emprestimo_categorias`, `emprestimo_itens`, `emprestimos_registro`, `emprestimo_bloqueios`, `alunos_cache`, `contatos`, `contato_cursos`, `emprestimo_relatorio_rede_pontos`, `app_migracoes` (marcador de backfills de dados que só podem rodar uma vez).

Migrations em [supabase/migrations/](supabase/migrations/) — rode **nesta ordem** no SQL Editor (dev e prod): `emprestimos_schema.sql` (schema-base do módulo, antes criado à mão — só documenta; remove índices duplicados), `emprestimo_status_item_rpc.sql` (manutenção/liberação de item com trava), `trocas_sala_data_aula.sql`, `trocas_sala_semana.sql`, `trocas_sala_predio_unique.sql` (unicidade por prédio — o `onConflict` do front depende dela), `trocas_sala_replica_identity.sql` (REPLICA IDENTITY FULL — sem ela o Realtime não propaga DELETE de trocas para outros clientes), `contatos.sql`, `contatos_seed.sql` (diretório de contatos + carga inicial; o seed é `on conflict do nothing` sobre `slug`, então reaplicar não sobrescreve o que foi editado pela tela), `emprestimos_v2.sql` (pontos de empréstimo, bloqueios, colunas novas do registro; backfill único guardado em `app_migracoes`), `emprestimos_v2_rpcs.sql` (RPCs do balcão v2), `emprestimo_duracoes_recentes.sql` (base da previsão de volta do painel do balcão, uma linha por item), `emprestimos_relatorio.sql` (dados brutos e anônimos do relatório de empréstimos), `emprestimos_relatorio_rede.sql` (módulo, pontos por login e RPC do relatório da rede), `rls_policies.sql` (RLS multi-prédio — obrigatória), `views_privilegios.sql` (tira as views do alcance da anon key — ver regra abaixo), `grade_substituir_rpc.sql` (troca a grade do prédio numa transação — usada pela importação do PDF), `indices_desempenho.sql` (índices por prédio em grade/salas/avisos/usuarios_acessos), `auditoria_log.sql`, `emprestimos_limpeza.sql` (dropa as RPCs da v1 de empréstimos — **só depois do deploy do código v2**: merge → deploy da Vercel concluído → `npm run migrate`). Migrations **não** rodam automaticamente. Duas formas de aplicar: (a) colar cada arquivo no SQL Editor na ordem acima; ou (b) `npm run migrate`, que roda todas via `psql` nessa mesma ordem ([scripts/migrate.mjs](scripts/migrate.mjs)) — requer `DATABASE_URL` no `.env` (Session pooler, porta 5432; **não** é a service_role key). Toda migration é idempotente, então reaplicar tudo é seguro (não há tracking de "já aplicadas"); ao adicionar uma nova, inclua-a no array `ORDEM` do script. Ao editar `rls_policies.sql`, reaplique.

**Toda função `SECURITY DEFINER` precisa de `set search_path = public` e de `revoke all on function ... from public, anon, authenticated` + `grant execute ... to service_role` no PRÓPRIO arquivo que a cria.** O Supabase concede EXECUTE a `anon`/`authenticated` em toda função nova do schema `public`, e a anon key é pública (vai no bundle do site): sem o REVOKE, qualquer pessoa chama a função em `/rest/v1/rpc/<nome>` com privilégio de dono, ignorando RLS, módulo e prédio — foi assim que `estatisticas_emprestimos` expunha nome e matrícula de alunos até 2026-11-05. O REVOKE fica no mesmo arquivo porque o runner reaplica tudo e um `DROP`+`CREATE` devolve os grants padrão. Exceção consciente: função chamada pelo front com sessão (ex.: `limpar_trocas_antigas`, pela Timeline) mantém `authenticated` e só perde `anon`. Conferir com `has_function_privilege('anon', oid, 'execute')` no catálogo — ou rodar `npm run auditar:banco` ([scripts/auditar-banco.mjs](scripts/auditar-banco.mjs)), que confere views, funções, RLS, Storage e o cadastro público do Auth; rode depois de mexer no banco pelo painel.

**Toda view no `public` precisa de `revoke all on table <view> from public, anon, authenticated` no PRÓPRIO arquivo que a cria** (e `grant select ... to service_role` se a API usa). View **não passa pela RLS** das tabelas de baixo — roda com o privilégio do dono — e o Supabase concede tudo a `anon`/`authenticated` em objeto novo do `public` (o event trigger `ensure_rls` liga a RLS só em tabela, não em view). Foi assim que `vw_equipe_predio` (join com `auth.users`) entregava e-mail, nome e permissões de todos os usuários a qualquer um com a anon key até 2026-11-05 ([views_privilegios.sql](supabase/migrations/views_privilegios.sql)). `security_invoker = true` só serve se a role que consulta puder ler as tabelas de baixo — a `service_role` **não** lê `auth.users`, então para `vw_equipe_predio` a correção é o REVOKE.

Esta linha é o consentimento explícito para essa ação.

**Trocas de sala (alteração de aula):** vivem em `trocas_sala`, escritas **direto pelo front** (anon key, [Timeline.jsx](src/components/Timeline.jsx)), tabela **separada da grade** (o re-import só mexe em `grade`, então as trocas sobrevivem). A chave é `predio_id` + `aula_unique_key = "<dia_semana>-<sala>-<periodo_inicial>"` + `semana` (segunda-feira ISO): estável ao re-import (não depende de `nome_aula`), distingue dias e prédios (salas de mesmo número existem em prédios diferentes). **Uma troca vale para UMA data** (regra do usuário: só aquela aula, naquele dia, naqueles períodos), e `semana` + o dia da chave identificam essa data. No front, um dia da semana significa sempre a **próxima ocorrência dele, hoje incluso** (`getProximosSeteDias`/`getProximaOcorrencia` do timeHelpers): numa quinta, "Segunda" é a segunda que vem. O seletor de dia da Linha do tempo mostra os 7 dias a partir de hoje com a data, a Timeline grava `semana` da data da aula (dá para registrar com antecedência) e o cartaz imprime a data. A leitura busca a semana atual e a seguinte e `trocasVigentes()` ([aulasDoDia.js](src/utils/aulasDoDia.js)) mantém de cada dia só o registro da próxima ocorrência; troca de dia que já passou some na hora, e `limpar_trocas_antigas` apaga as semanas anteriores. Gravar com `getSemanaAtual()` é o bug antigo: na quinta, a troca de "Segunda" caía na segunda que já passou e sumia no dia da aula. A troca serve também para **união de aulas** (destino já ocupado) e geralmente vai para **outro prédio**: não acople trocas ao módulo Salas Livres. **Fluxo na tela (como numa agenda):** clicar numa aula da Timeline abre o [ModalAulaTroca](src/components/ModalAulaTroca.jsx) (detalhes, para todos; também serve ao balcão), com o botão explícito "Trocar de sala" → [ModalTrocaSala](src/components/ModalTrocaSala.jsx) (data, períodos e destino primeiro; dados do cartaz recolhidos; "Salvar" e "Salvar e imprimir aviso"). O botão "🔁 Trocas" da toolbar e o número laranja da aba (navega para `?trocas=<timestamp>`, prop `abrirTrocas`) abrem o [ModalListaTrocas](src/components/ModalListaTrocas.jsx) (trocas de hoje a +6 dias, via `listarTrocas()`: ver na grade, reimprimir, editar, desfazer). A aula de uma troca vem de `blocoDaChave()` (aulasDoDia). O cartaz é gerado só em [cartazTroca.js](src/utils/cartazTroca.js) (`gerarHtmlCartaz`, puro e testado; logos por parâmetro). Sem `edicao_grade` (prop `canEditGrade`), painel e lista ficam só em consulta (reimprimir). Cálculos de "agora" (dia, período, semana) usam sempre o fuso `America/Sao_Paulo` via `getDataSaoPaulo()` do timeHelpers — nunca o fuso do browser.

## Convenções e armadilhas

- ESLint ([eslint.config.js](eslint.config.js)) tem dois blocos: `src/**` (globals de browser, regras react-hooks/react-refresh) e `api/**` + `backend_core/**` (globals de Node). `no-unused-vars` ignora nomes `^[A-Z_]`.
- Erros da API sempre voltam como `{ error: mensagem }`. No front, leia com `lerResposta(res)` ([utils/api.js](src/utils/api.js)) — usa o `data.error` do servidor e traduz status sem JSON (413 da Vercel, 502/504). Não copie um `parseResponse` novo. No backend, exceção que escapa do handler vira 500 genérico no `withAuth` (falha de sessão → 401; Auth/banco fora → 503).
- **Telas "ao vivo" (dia/período atual):** use `useMomentoAtual()` ([hooks/useMomentoAtual.js](src/hooks/useMomentoAtual.js)) e leia `momento.periodo` **dentro** do `useMemo` e nas deps. Não crie relógio próprio com um `tick` que o memo não lê — o lint manda removê-lo da lista de deps e a tela congela (foi o bug da Planta ao Vivo até 2026-11-05). A Timeline ainda tem o relógio próprio (correto, mas é o padrão antigo).
- **HTML montado à mão** (janelas de impressão com `document.write`, que são da mesma origem e veem a sessão): todo valor passa por `escaparHtml`/`numeroSeguro` ([utils/html.js](src/utils/html.js)). **CSV:** toda célula por `celulaCsv` ([utils/csv.js](src/utils/csv.js)) — valor começando com `= + - @` vira fórmula no Excel.
- **Senha:** regra única em [senha.js](backend_core/utils/senha.js) (mínimo 8, compartilhado front+back). **Equipe:** as travas de quem altera quem (admin só por admin; ninguém revoga a si mesmo) são funções puras em [equipeRegras.js](backend_core/utils/equipeRegras.js) — o handler só aplica.
- Em mutações, desabilite o botão de submit enquanto a operação está pendente (`isPending`/`isCriando`) — padrão já seguido nos modais.
- **Empréstimos = pontos de empréstimo.** Um prédio tem um ou mais **pontos** (`emprestimo_pontos`, ex.: Recepção → jogos, Secretaria → carregadores), cada um com acervo (categorias → itens), limite de itens por aluno (`limite_por_aluno`) e atendentes próprios (`emprestimo_ponto_usuarios`, editado na Gestão de Equipe quando o membro tem o módulo `emprestimos`). Quem tem `emprestimos` opera **só os pontos vinculados**; `gestao_emprestimos` e admin veem todos; o relatório vê o prédio todo com `relatorios`/gestão/admin. `emprestimos_registro` guarda `predio_id`/`ponto_id` do momento da retirada (trigger `trg_emprestimo_registro_local`), e a RLS `reg_select` usa `app_tem_ponto()` — o payload do Realtime traz nome e matrícula, então outro ponto do mesmo prédio não recebe os eventos. Toda regra atômica (item livre, acervo ativo, suspensão, limite do ponto, devolução OK/COM_PROBLEMA/NAO_DEVOLVIDO, desfazer em 10 min) vive nas RPCs de [emprestimos_v2_rpcs.sql](supabase/migrations/emprestimos_v2_rpcs.sql); regras puras (nome padronizado, janela de desfazer, mediana/previsão de volta) em [emprestimoRegras.js](backend_core/utils/emprestimoRegras.js), compartilhado front+back como o timeHelpers e testado em `tests/emprestimoRegras.test.js`. **`JANELA_DESFAZER_MIN` espelha o `interval '10 minutes'` de `emprestimo_cancelar`/`emprestimo_reabrir` — ao mudar um, mude o outro.** Item que "não voltou" fica `PERDIDO` (registro `EXTRAVIADO`); retirada desfeita fica `CANCELADO` e não entra em estatística nem na previsão. Não há prazo de devolução por decisão do usuário: a previsão ("costuma voltar em ~15 min") é só a mediana das últimas devoluções do item (ou da categoria, com < 5 amostras). As durações vêm **já recortadas pelo banco** (RPC `emprestimo_duracoes_recentes`: até 30 por item, limites em `PREVISAO_VOLTA`, que o repository repassa à RPC); a conta continua em `calcularMedianas()`. O painel recarrega a cada minuto em cada PC do balcão, então não volte a trazer registros brutos: eram até 1.500 por recarga (~200 KB), o maior gasto de tráfego do Supabase gratuito.
- **Relatório de empréstimos é ANÔNIMO** (decisão do usuário, 2026-11-05: nome e matrícula de aluno são dados confidenciais). `GET /api/emprestimos/relatorio` → RPC `emprestimo_relatorio` devolve só retiradas (item, ponto, horários, situação), acervo, pontos e `retiradasPorAluno` (quantas retiradas cada aluno fez, sem identificar) — nem um código por aluno vai nos registros. Toda conta da tela, do PDF e da planilha sai de `montarRelatorio()` em [relatorioEmprestimos.js](src/utils/relatorioEmprestimos.js) (puro, testado); o PDF é desenhado com jsPDF em [pdfRelatorioEmprestimos.js](src/utils/pdfRelatorioEmprestimos.js) (vetorial, tema claro, cabeçalho com prédio/ponto/período). O PDF é **só o resumo** — cartões e gráficos, **sem a lista de retiradas** (decisão do usuário, 2026-11-05); a lista fica na tela e na planilha. Não volte a fotografar a tela (html2canvas): saía com ~30 MB, no tema escuro e sem o filtro. Acima de `MAX_RETIRADAS_RELATORIO` (12 mil, [limites.js](backend_core/utils/limites.js)) a API pede um período menor — a resposta passaria dos 4,5 MB da Vercel. O usuário recusou cartões de "em aberto" e "não devolvidos" no relatório.
- **Relatório da rede (vários prédios).** Pedido da coordenação da recepção: acompanhar os jogos retirados nas recepções de todos os prédios (para apresentações) sem ser admin. Módulo `relatorio_emprestimos_rede` + tabela `emprestimo_relatorio_rede_pontos (user_id, ponto_id)`: os pontos que o login vê, **escolhidos um a um no Painel Admin** (atalho "Todos 'Recepção'"); ponto novo não entra sozinho. Os dados são os mesmos do relatório do prédio, **anônimos** (RPC `emprestimo_relatorio_rede`, pela lista de pontos e com o prédio de cada um; `retiradasPorAluno` conta o aluno uma vez na rede). API: `GET /api/emprestimos/rede/pontos` e `GET /api/emprestimos/rede/relatorio?inicio=&fim=&pontos=a,b` — nunca usam o prédio do login; ponto fora da lista → 403; admin vê todos os pontos. Tela: a mesma [RelatoriosEmprestimos](src/components/RelatoriosEmprestimos.jsx) com `rede` (rota `ROTAS.relatorioEmprestimosRede`; filtro por prédio ou ponto via `selecaoDaRede()`); com mais de um prédio, [montarRelatorio()](src/utils/relatorioEmprestimos.js) conta por prédio, mostra o ponto como "Prédio 15 · Recepção", soma os itens de mesmo nome no ranking (o jogo, não o exemplar) e a planilha ganha a coluna Prédio. O login da coordenação tem **prédio nulo**: o Dashboard não o trata como órfão e mostra só o topo + o relatório, também na raiz `/` (sem redirect, por causa do hash do convite); as outras rotas da API seguem recusando por falta de prédio/módulo. **Só o admin concede ou retira** (`MODULOS_SO_ADMIN` em [modulos.js](backend_core/utils/modulos.js)): a Gestão de Equipe não mostra o módulo, o `sanitizarPermissoes(..., { atuais })` mantém o que o membro já tinha, e reconvite/revogação de quem o tem são barrados ([equipeRegras.js](backend_core/utils/equipeRegras.js)) — o reconvite prenderia o login a um prédio.
- **Empréstimos com login compartilhado.** Os PCs da recepção usam a mesma conta; cada navegador guarda seu nome ("Balcão 1") em `localStorage.balcao` e o seu ponto em `localStorage['balcao_ponto:<predio>']` ([utils/balcao.js](src/utils/balcao.js)). O nome vai no header `x-balcao` (URL-encoded) e é gravado em `balcao_retirada`/`balcao_devolucao` (até 2026-11 ia junto do e-mail em `resp_*` como `"email · Balcão 1"` — o service aceita os dois). O balcão é para leitor de crachá: o campo de bipagem recebe o foco de volta sozinho (exceto se o foco estiver noutro campo de texto ou o usuário navegar com Tab), Esc cancela, e na tela de devolução um crachá bipado abre o próximo atendimento em vez de confirmar a devolução anterior. Sons em [somBalcao.js](src/utils/somBalcao.js) (liga/desliga por PC). Modais do UIContext têm `data-ui-modal` — o foco não é devolvido enquanto um modal está aberto.
- **Troca de titular** (pedido do usuário, 2026-11-05): o item passa de um aluno para outro sem voltar ao balcão — o crachá retido passa a ser o do novo aluno. RPC `emprestimo_transferir` ([emprestimos_v2_rpcs.sql](supabase/migrations/emprestimos_v2_rpcs.sql)), numa transação: o registro de quem passou fica `TRANSFERIDO` (encerrado, `data_devolucao` = hora da troca; **não** é devolução — fica fora da previsão de volta, que só usa `CONCLUIDO`, e não é reabrível pelo "desfazer devolução") e nasce um `ATIVO` com `transferido_de` apontando para ele; o item fica `EMPRESTADO` o tempo todo (o outro PC nunca o vê livre). Suspensão e limite do novo aluno vêm de `emprestimo_validar_aluno`, a **mesma** função da retirada (interna: sem EXECUTE para ninguém, nem `service_role`). Desfazer a troca = `emprestimo_cancelar` no registro novo: com `transferido_de`, reabre o anterior em vez de liberar o item (o front manda `tipo: 'troca'` só para o texto). No relatório **cada titular conta como uma retirada** (decisão do usuário) e quem passou aparece como "Passou a outro aluno", com o tempo de uso dele (`situacaoDe` em [relatorioEmprestimos.js](src/utils/relatorioEmprestimos.js)). O item não passa pela conferência do balcão: problema ou "não devolveu" depois fica com o novo titular (decisão do usuário). Front: botão "🔁 Trocar titular" ao lado da devolução (card Em andamento e tela de devolução do wizard) → `ModalTrocaTitular` no [MuralEmprestimos](src/components/MuralEmprestimos.jsx): bipa o crachá → `GET /aluno/:mat` mostra suspensão/limite → nome se for a 1ª vez → Enter confirma (`POST /transferir/:id`). O submit do modal **nunca** fica `disabled` (só `aria-disabled`): com submit desabilitado o navegador ignora o Enter do campo e o leitor não consegue nem consultar. Histórico mostra "Passou para X"/"recebeu de Y" (nomes resolvidos no service por `getNomesDasTrocas`, sem troca desfeita). Auditoria `emprestimo.transferir` (de → para).
- **Falha ao carregar permissões ≠ conta órfã.** [useAuthAccess](src/hooks/useAuthAccess.js) devolve `erro` + `recarregar()`; o Dashboard mostra "Tentar de novo" em vez de "Acesso Restrito". O objeto retornado é memoizado (efeitos como o do SeletorPredio dependem da identidade de `acesso`).
- **Planos gratuitos (Supabase Free + Vercel Hobby).** Volume não é o problema (análise de 2026-11-05: com o balcão o dia todo, ~20% das chamadas de função da Vercel e ~35% do tráfego do Supabase). Os riscos são outros. (1) O Supabase pausa o projeto depois de **7 dias sem atividade** (recesso): o cron diário da Vercel (`/api/equipe`, reconhecido por `ehChamadaDoCron()` em [cron.js](backend_core/utils/cron.js)) faz um SELECT via [saude.service.js](backend_core/services/saude.service.js). Não o faça responder sem tocar no banco (era assim até 2026-11-05). Se `CRON_SECRET` for configurado na Vercel, só o `Authorization: Bearer` vale. (2) O plano gratuito **não tem backup restaurável**: `npm run backup` ([scripts/backup.mjs](scripts/backup.mjs)) faz pg_dump de `public` + `auth` (sem dados de sessão), confere o arquivo com `pg_restore --list`, guarda os `BACKUP_MANTER` mais recentes (padrão 8) e recusa pasta dentro do repositório, que é público. (3) O Hobby da Vercel é para uso pessoal e não comercial; estourar uma cota lá não gera cobrança, a função para até fechar 30 dias.
- `.env` (local) e Environment Variables na Vercel (prod). Prefixo `VITE_` = exposto ao browser; sem prefixo = só backend. `SUPABASE_SERVICE_ROLE_KEY` **jamais** com `VITE_`. Veja [.env.example](.env.example).
- **Convite de equipe depende do provedor de e-mail do Supabase.** `POST /api/equipe/convidar` chama `auth.admin.inviteUserByEmail`; com o serviço de e-mail **interno** do Supabase (sem SMTP próprio) o limite padrão é de **2 e-mails/hora** e o 3º convite volta `email rate limit exceeded` (429). Corrija em Authentication → Emails/SMTP (SMTP próprio) + Auth → Rate Limits. No código, todo erro do GoTrue passa por `traduzirErroDeConvite()` em [convite.js](backend_core/utils/convite.js) (junto de `urlDoApp`, `emailPermitido` e `ehContaExistente`, usados pela Gestão de Equipe e pelo Painel Admin) — nunca deixe erro de provedor virar 500 genérico.
- **Conta nova pelo Painel Admin** (`POST /api/admin/usuarios`, `criarUsuario()` em [admin.service.js](backend_core/services/admin.service.js)): já com prédio, cargo, módulos, pontos do balcão (do prédio escolhido) e pontos da rede. Dois modos: **convite** (e-mail com link, mesmo limite do provedor) ou **senha definida pelo admin** (`auth.admin.createUser` com `email_confirm: true`, nenhum e-mail sai — a saída quando o limite de e-mails estoura). E-mail que já tem conta dá 409 e não é sobrescrito (o admin usa "Editar Acesso"); conta sem prédio só com Administração ou Relatório da Rede (senão nasceria órfã); se os acessos não gravam, a conta do Auth é apagada. Auditoria `admin.usuario.criar`. A Gestão de Equipe continua sendo o convite por prédio; para o admin ela mostra a equipe do prédio escolhido no topo.

Nunca derive essa URL do header `Host` — seria open redirect.
